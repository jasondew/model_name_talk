The `id` on each slide is the key. Keep it and the edit lands on that slide;
change the heading text beside it and you have retitled the slide. To add a
slide, write a new heading with an id nobody else is using. To cut one,
delete its block. To move one, move its block.

Note lines carry their meaning in the first character, and they are what the
speaker reads, never what the slide should look like:

- a cue, a short phrase
! a point that has to be made out loud, drawn lit on the speaker's screen

`[stub]` means the content is written but nobody has drawn the slide yet, so
it renders hatched with its title and notes showing. That is not a fault to
fix here; it is a drawing job.

`minutes` includes the round that closes the chapter. `lands` is the one

### `not_specialists` They are not subject specialists

```
! There is no maths expert and no French expert
! Routing is learned for each token and each layer, and a person usually cannot read it
- This is the most common wrong idea about MoE, so say it plainly
- If somebody asks what expert 47 does, the honest answer is that nobody knows
```

### `memory_and_speed` Total sets memory. Active sets speed.

*2 steps*

```
! Every expert has to be in memory, because the next token may want a different one
! But each token only uses about 3B of those 30B parameters
! 3B is not one expert. It is 8 small experts plus the attention and embeddings every token uses
- Each expert is about 226M across all 48 layers. All 128 of them are 29B, 95% of the model
- Total is 1.5B shared plus 128 experts. Active is the same 1.5B plus 8
- So it costs a 30B model to hold and runs near the speed of a 3B one
- Attention is not split. Every token uses all of it
- If a name has no A segment, assume dense
```

= Mixture of Experts: a design where each layer has many small feed forward blocks and each token uses only some
= expert: one of those feed forward blocks
= router: the small network that picks the experts for each token
= active parameters: the parameters one token actually uses

### `why_quantize` 61 GB, and a 12 GB GPU

*3 steps*

```
! This is why quantization exists. Not to be clever, to make it fit
- Qwen3-30B at the precision Qwen released it, BF16, 2 bytes each: 61 GB
- The GPU in my machine, an RTX 3060, holds 12
- Quantization is the whole distance between those two numbers
- It also makes it faster, which we come back to
```

### `precision` Bits for each weight

*2 steps*

```
- FP32 is four bytes, BF16 two, INT8 one, four bit is half a byte
! Vendors release at 16 bits. That is why it is 61 GB and not 122
- At FP32 this model would be 30.5B times 4 bytes, 122 GB. Nobody ships that
- BF16 halves it with essentially no loss, so the release is already the first halving
- Everything in this chapter is about spending fewer bits on each number
```

### `the_formula` parameters x bits

```
! If they remember one thing from this talk, this is it
- Parameters in billions times bits for each, divided by 8, gives gigabytes
- 30.5B at 16 bits is 488 billion bits, over 8 is 61 GB. That is the release
- Say it once, slowly, and let it sit
```

### `the_method` A scale, and sixteen levels

*3 steps*

```
- Cut the weights into small blocks, 32 of them at a time
- Store one scale for the block, then a small integer for each weight
- Four bits gives you sixteen levels to land on. That is the whole trick
- Walk the worked example. Multiply the integer by the scale to read a weight back
```

### `why_blocks` One huge weight would ruin a whole tensor

```
! Small blocks keep the damage local
- One outlier in a block of 32 spoils 32 numbers, not 30 billion
- This is the entire reason blocks exist
```

### `the_label` Q4, K, M

*4 steps*

```
- Q4: four bits for each weight
- K: llama.cpp's k-quant, which also quantises the scales
- M: medium. S, M and L exist. The sensitive tensors keep more bits
- So the label is three separate decisions stuck together
```

### `the_real_cost` 34 bytes for 32 weights

*2 steps*

```
! Q8_0 is not 8 bits for each weight. It is 8.5
! Every block of 32 carries a 2 byte scale, and that scale is not free
- Four lines of C from ggml-common.h. This is the primary source
- 34 times 8 over 32 is 8.5. Do the arithmetic on the slide
- This is exactly why the naive formula comes out low
```

### `comparing_types` What the labels actually cost

*5 steps*

```
- Same model, same 30.5 billion parameters, four real files
- BF16 is what Qwen released. Everything below it is somebody else's conversion
! Q4_K_M is the usual deal and it is under a third the size
- Q2_K does fit the 12 GB GPU, and you would not enjoy it
- The bar is bits for each weight, the number beside it is the file on disk
```

### `does_it_work` The formula against real files

*3 steps*

```
! Within about one percent, every time
- These are real file sizes from Hugging Face, checked this week
! The gap is not overhead to apologise for. It is the wrong constant
- Put 4.8 in for Q4_K_M rather than 4, and the formula is right
- That is a better thing to remember than a rule with an excuse attached
```

### `quality_and_speed` Rules of thumb, and they are rules of thumb

```
! Say out loud that these are rules of thumb, not measurements
- 8 bits is nearly lossless. 4 bits is the usual deal
- Below about 3 bits quality falls off a cliff
- Quantising also makes it faster. Generation is memory bandwidth bound, fewer bytes to move
```

### `not_just_weights` The weights are not the whole bill

```
- The KV cache stores keys and values for every previous token so they are not recomputed
- It grows with the context length
- One sentence only. This is a whole talk on its own and not this one
```

= block and scale: a small group of weights, and the number that converts their integers back
